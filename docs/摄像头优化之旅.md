# 摄像头实时流优化记录

## 问题现象

打开摄像头后，画面严重卡顿，无法实现实时效果预览。

---

## 优化步骤

### 1. UI 加载失败

**问题**  
浏览器控制台报错：`Uncaught SyntaxError: Identifier 'uploadOverlay' has already been declared`

**原因**  
前端 JavaScript 有重复的变量声明

**解决**  
移除重复的 `const` 声明，确保脚本正常加载

**结果**  
UI 正常显示

---

### 2. WebView2 MJPEG 断流

**问题**  
尝试用 `multipart/x-mixed-replace` 发送 MJPEG 流，但 WebView2 在几秒后自动断开

**原因**  
Windows WebView2 对长连接 MJPEG 流的支持不完整

**解决**  
改用前端 fetch 轮询 + Blob URL 方案
- 前端通过 `requestAnimationFrame` 高频请求 `/api/video_snapshot` 单帧接口
- 后端返回打包好的 JPEG 字节流
- 前端生成 Blob URL 显示在 img 标签中

**代码示例**  
```javascript
function loopVideoSnapshot() {
    fetch('/api/video_snapshot')
        .then(response => response.blob())
        .then(blob => {
            const url = URL.createObjectURL(blob);
            mainCanvasImage.src = url;
            mainCanvasImage.onload = () => {
                URL.revokeObjectURL(oldSrc);
                setTimeout(() => requestAnimationFrame(loopVideoSnapshot), 30);
            };
        });
}
```

**结果**  
摄像头画面可以显示，但仍然卡顿

---

### 3. 帧率优化初步

**问题**  
摄像头虽然能显示，但画面卡顿，帧率低下

**优化措施**
- 前端轮询增加 30ms 缓冲，限制最大请求频率为 ~33fps
- 后端配置 OpenCV：
  - `CAP_PROP_BUFFERSIZE=1` - 防止帧缓存积压
  - 分辨率限制为 640×480
  - JPEG 质量降低到 60 - 加快编码速度

**结果**  
略有改善，但仍然卡顿

---

### 4. 后台线程架构重构

**根本问题**  
每个前端请求都会触发 Flask 同步执行：
1. `capture.read()` - 硬件读取（阻塞）
2. 图像处理（可选）
3. JPEG 编码

所有工作在单个请求线程中串行执行，前端高频轮询会导致请求堆积。

**解决方案**  
独立后台线程专门负责视频采集和处理，HTTP 接口只负责返回缓存

```python
def _video_reader_loop():
    while is_active:
        success, frame = capture.read()
        frame_bytes = _encode_frame(frame)
        with lock:
            video_state["latest_frame_bytes"] = frame_bytes

@app.route("/api/video_snapshot")
def video_snapshot():
    with lock:
        frame_bytes = video_state["latest_frame_bytes"]
    return Response(frame_bytes, mimetype="image/jpeg")
```

**结果**  
明显改善，但仍有残留卡顿

---

### 5. 移除默认实时滤镜

**发现根因**  
检查初始化代码发现：

```javascript
let currentAction = 'mean_filter';  // 默认激活均值滤镜
```

摄像头启动时，后台线程对每一帧都进行纯 Python 均值滤波：

```python
def mean_filter(image, kernel_size=3):
    for u in range(w):
        for v in range(h):
            # 双重循环处理每个像素
            filtered_image[v, u] = window.mean(axis=(0, 1))
```

对 640×480 图像，这意味着每秒约 920 万次像素处理循环（30fps 下）。

**解决方案**  
视频模式默认不应用任何实时特效，只在用户手动选择滤镜时启用

```javascript
let videoAction = null;  // 视频模式使用独立的动作状态

function startVideoStream() {
    videoAction = null;  // 默认无特效
    loopVideoSnapshot();
}
```

**结果**  
✓ 流畅运行，30fps 稳定输出

## 总结

| 步骤 | 问题 | 解决方案 | 结果 |
|-----|------|--------|------|
| 1 | JavaScript 重复声明 | 移除重复的 const | UI 加载正常 |
| 2 | WebView2 MJPEG 断流 | fetch + Blob 轮询 | 画面能显示 |
| 3 | 帧率低下 | 前端限流、分辨率/质量调优 | 小幅改善 |
| 4 | 单线程串行处理 | 后台采集线程 + 缓存架构 | 显著改善 |
| 5 | 默认运行高成本算法 | 移除默认实时滤镜 | **流畅运行** ✓ |

## 关键经验

1. **识别真正的瓶颈** - 最后一个简单的改动（移除默认滤镜）比所有复杂的优化都有效
2. **架构优于微优化** - 后台线程的引入彻底改变了系统特性，单纯调参改不了
3. **不同限制需要不同方案** - WebView2 的限制需要改变传输模式，而不是在原模式上挤压性能
4. **逐步验证很重要** - 每个步骤都带来了可测量的改进或关键信息
